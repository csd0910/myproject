# バウンスメール解析ツール 開発・改修ガイド（プロンプト用資料）

このドキュメントは、バウンスメール（不達メール：Delivery Status Notification など）を解析・集計するスクリプトを新たに生成・改修する際に、AI（LLM）に要件として渡すためのテンプレートおよび仕様書です。
**次に似たようなツールを作る際や、機能追加を行う場合は、このファイルの内容をプロンプトとしてAIに提示してください。**

---

## 1. バウンスメール解析における特有の壁と注意点（AIに必ず認識させるべき前提知識）

バウンスメールの構造は送信元（Google, Microsoft, キャリアメール, 独自ドメイン）によってフォーマットがバラバラです。開発時は以下のリスクを考慮して堅牢に実装させる必要があります。

1. **文字コード（エンコーディング）の混在**
   - 日本語のメール環境では `utf-8` 以外にも `iso-2022-jp` や `cp932` が頻繁に混在します。単純に `.decode('utf-8')` とするとエラーで止まったり、文字化けで情報が欠落します。
2. **MIMEエンコードのヘッダー (`=?ISO-2022-JP?B?...?=`)**
   - SubjectやToなどがエンコードされている場合、適切に `email.header.decode_header` でデコードをつなぎ合わせる必要があります。
3. **RFCに準拠しないバウンスメールの存在**
   - 理想的には `multipart/report` と `message/delivery-status` を読めば値が取れますが、携帯キャリアや一部のサーバーは単なる `text/plain` に英語でエラーを残すだけです。
   - 対策として**「RFC構造解析」と「正規表現による全文スキャン」の二段構え（ハイブリッド解析）**が必須です。
4. **Excel出力時の制御文字によるエラー**
   - メール本文に含まれる見えない制御文字（NUL文字など）のせいで、`openpyxl` がエラーを吐いて保存に失敗します。保存前の文字列クリーニングが必須です。

---

## 2. システムの基本構造（標準アーキテクチャ）

スクリプトは以下のモジュール/関数に分けて実装します。

- **文字コードユーティリティ**
  - バイト列に対し、複数の文字コードリスト（utf-8, iso-2022-jp, cp932等）を順に試してデコードする安全な関数。
  - Excel出力不能な文字（ILLEGAL_CHARACTERS）を除外・サニタイズする関数。
- **入力ローダー**
  - EMLファイル単体、EMLが複数入ったフォルダ、mboxファイル（Thunderbird等）を自動で判別し、Mailオブジェクトのジェネレータを返す機構。
- **抽出・解析エンジン（ハイブリッド方式）**
  - **第一段階:** `message.walk()` で `message/delivery-status` を探し、`Final-Recipient` や `Diagnostic-Code` を抽出。
  - **第二段階:** 本文と全ヘッダーを含めた巨大な文字列を作成し、正規表現で `SMTPコード (5.x.x 等)` やメールアドレスを強制抽出。
- **原因の日本語翻訳モジュール**
  - 抽出した3桁のSMTPコード（例: 550, 421等）とテキストを、「不在」「満杯」「一時的エラー」といったビジネスユーザーが理解できる日本語ラベルに変換する辞書とロジック。
- **Excel (.xlsx) / CSV 出力モジュール**
  - 出力列定義、カラーリング（エクセルの場合）、列幅の自動調整。

## 3. 次回作成時用：AIへのプロンプト・テンプレート

以下をコピーしてAIのチャット欄に貼り付けることで、高品質な解析ツールを最初から出力させることができます。

```text
【依頼概要】
様々な形式のバウンスメール（不達メール）を読み込み、構造解析と正規表現全文スキャンを組み合わせた堅牢な解析スクリプトをPythonで作成してください。

【アーキテクチャと必須要件】
1. 解析の「二段構え」ハイブリッドロジック
   - 第一段階: `multipart/report` 内の `message/delivery-status` パートを解析し、正規の RFC3464 フォーマットから抽出。
   - 第二段階: 取得できなかった場合、メール本文と全ヘッダーをつなげた文字列に対し、正規表現（例: `r"5\.\d\.\d"` や宛先アドレス抽出パターン）をかけてフォールバック取得。
2. エンコーディングの聖域化
   - `email.header.decode_header` と独自関数を使用し、utf-8、iso-2022-jp、cp932等が混在していても絶対に処理落ちや文字化けをさせないこと。
   - openpyxlでExcelエラーにならないよう、制御文字を除去するクリーニング処理を通すこと。
3. 日本語でのエラー詳細化
   - 抽出したSMTPステータス（3桁コードや5.x.x）と Diagnostic-Code の本文を読み取り、以下の辞書をベースに具体的な日本語の理由（例：「【421エラー】ドメインサービスが利用不可」「【満杯】相手の容量不足です」等）を出力列に含めること。
4. 入力と出力
   - 入力：mboxファイル、EMLファイル単体、EMLが格納されたフォルダを自動で認識しループ処理。
   - 出力：Excel (.xlsx)形式。エラー種別ごとに背景色（赤、オレンジなど）を塗り分けること。

【抽出してほしい列】
- 受信日時
- 宛先メールアドレス（バウンス先）
- 3桁のSMTPコード
- 詳細診断コード (Diagnostic-Codeの原文)
- ★日本語判定結果（例: 【550エラー】メールボックス利用不可（不在））
- 責任分界点（自社サーバー か 相手サーバー かをRemote-MTA等から判定）
- SPF, DKIM, DMARC の認証結果（Authentication-Resultsなどから）
```

## 4. エラーコード対応表（辞書化用データ）

システム内部で用いる3桁のエラーコード辞書は以下のリストを利用し、スクリプト内に `dict` として埋め込んでください。

| コード | 説明 |
| --- | --- |
| 101 | 無効なSSLまたはTLS設定 |
| 111 | リモートSMTPサーバーへの接続エラー |
| 221 | ドメインサービスが送信チャネルを閉じています |
| 250 | 要求されたメールアクションが完了しOK |
| 420 | 受信者のファイアウォール/フィルターがメールをブロック |
| 421 | ドメインサービスが利用不可、送信チャネルを閉じています |
| 422 | 受信者のメールボックス容量超過 |
| 431 | ストレージ不足またはメモリ不足 |
| 441 | 断続的なネットワーク接続、サーバー応答なし |
| 446 | ホップ数が多すぎる（ループの可能性） |
| 447 | タイムアウト発生、サーバー接続確認 |
| 450 | メールボックス利用不可、要求拒否 |
| 451 | ローカル処理エラー、再試行 |
| 500 | 構文エラー、コマンド認識不可 |
| 511 | メールボックスが見つからない（不在） |
| 512 | ドメインが見つからない、ホスト不明 |
| 522 | 受信者メールボックス容量超過（満杯） |
| 530 | アクセス拒否、認証必要 |
| 550 | メールボックス利用不可（不在・拒否） |
| 554 | トランザクション失敗 |
| 556 | 受信サーバーが処理できないほどメッセージ大 |
*(※代表的なものを抜粋。実際のコード内ではフルサイズを実装)*

---

**（開発担当者へ）**
バウンスの解析は「絶対に例外でプログラムを落とさない」ことが鍵です。様々なパターンのスパムや不正なヘッダーが混在していることを考慮し、`try-except`ブロックを適切に配置して「解析不能なメールはスキップして次へ進むか、Unknownとして記録する」設計を心がけてください。
