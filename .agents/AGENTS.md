## 開発・コーディングにおける厳格な行動規範
**対象言語: Python / JavaScript / HTML / CSS / PowerShell / ExcelVBA すべて共通**

以下のルールはAIエージェントのコンテキスト肥大化・クォータ超過・処理タイムアウトを防止するために設けられています。**機能追加・修正を行う前に必ず確認すること。**

### 1. 単一責任とファイル行数の上限（300行ルール）
- **1ファイルあたりのコード量は原則 200〜300行以内** を厳守すること。
- 1つのファイルに複数の責務（HTML構造・CSS・JavaScript・ビジネスロジック・設定値など）を混在させないこと。
  - HTML → 骨格のみ。スタイルは `.css`、ロジックは `.js` へ分離。
  - Python → APIエンドポイント / ビジネスロジック / DB操作 / ユーティリティを別モジュールに分離。
  - 設定値・パス・定数は直書きせず、設定ファイルまたは定数モジュールに集約する。
- 既存ファイルが **400行を超えている場合**、または責務が肥大化していると判断した場合は、機能追加を行う前に「モジュール分割リファクタリング案」をユーザーに提示し、承認を得てから着手すること。

### 2. コンテキスト最適化とトークン節約
- コード修正時は、**無関係なファイル全体を再生成・全行走査しない**こと。変更対象の関数・クラス・セクションのみをピンポイントで修正（Diff形式）すること。
- インラインに長大なデータを埋め込まないこと。
  - ❌ 禁止例: Base64エンコード画像、1000文字超のSVGインライン、巨大なモックJSONをコード内に直書き
  - ✅ 推奨例: 外部ファイル（`assets/`, `data/`, `config/`）に分離して参照
- 一度に複数のファイルを大量に書き換えるコマンドを避け、**1ファイルずつ順番に処理**すること。

### 3. リファクタリングの自律提案
- ファイルを新規作成・既存ファイルを修正する前に、対象ファイルの行数・責務を確認する習慣を持つこと。
- 下記の条件に1つでも該当する場合は、修正を開始する前に分割案を提示すること：
  - ファイル行数が 400行超
  - 1関数・1クラスが 100行超
  - HTML / CSS / JS / Python ロジックが同一ファイルに混在

### 4. 安全な差分適用（ステップバイステップ原則）
- 大規模な変更（複数ファイルにまたがる修正、リファクタリング、新機能追加）は必ず以下の手順で実施すること：
  1. **計画の提示** → ユーザーの承認
  2. **1ファイルずつ** 変更を適用
  3. 適用後に動作確認を促す（サーバー再起動・ブラウザ確認など）
  4. 確認が取れてから次のファイルへ進む
- タイムアウトや差分衝突を防ぐため、一度のツール呼び出しで書き換える行数は **500行以内** を目安とすること。

## アプリ・ツール開発におけるUXと堅牢性の必須要件（Must-Have）
Python (Tkinter/NiceGUI等) やその他言語でGUIツール・自動化スクリプトを実装する際は、以下の要件を必ず組み込むこと。

### 1. フリーズ防止とスレッドセーフな更新（UIスレッドの保護）
- 重い処理（ファイル操作、API通信、大量データ処理など）は、必ずバックグラウンドスレッド（`threading` 等）や非同期処理で実行し、画面が「応答なし」になるのを絶対に防ぐこと。
- 別スレッドから画面（Tkinterなど）を更新する際は、直接操作せず、必ずGUIフレームワークの安全な仕組み（例：Tkinterの `after` メソッド等）を使って「メインスレッドに処理を委譲（予約）」すること。

### 2. 進捗の可視化とフェイルセーフの確保
- 処理の進行度合いがユーザーに伝わるよう、プログレスバーやステータス文字列（「〇〇を処理中... 3/10件完了」など）をUI上に必ず実装すること。
- ドラッグ＆ドロップなど特定の操作方法に依存したUIを作らず、必ず「クリックでファイル選択」などの確実な代替手段（予備ルート）を併設し、誰のどんな環境でも操作が詰まらないようにすること。

### 3. 利用者を不安にさせない事前告知（心理的UX）
- 処理中に「黒い画面が一瞬開く」「ブラウザが自動起動する」「警告画面が出る」といった特殊な挙動がある場合は、実行ボタンの近くに「※実行時に〇〇の画面が開きます」といった注意書きを明記し、利用者が戸惑わない設計にすること。

### 4. 環境差異の吸収（決め打ちの禁止）
- レジストリ位置やパスなど環境に依存する処理は、ハードコードを避け、If文でのメーカー・OS判定や外部設定ファイル（JSON等）への分離を行い、汎用性を持たせること。

### 5. 詳細なエラーロギングと技術的限界の早期判断
- 単なる `try-except` に留めず、エラー発生時は `traceback` モジュール等を活用し、「どのファイルの、どの関数の、何行目で、どんな処理中にエラーが起きたのか」が一目でわかるログをファイルまたはUIのダイアログに出力すること（`except Exception: pass` による握りつぶしは原則禁止）。
- 局所的なコード修正を繰り返しても精度や速度が出ない場合は無駄な固執を避け、API利用や全く別のアプローチなど、根本的な代替案を早期にユーザーへ提案すること。
## AIエージェント間の自律的連携・引き継ぎルール (Agent Collaboration Protocol)
複数のAI（Web版のAntigravity 2.0やIDEのAntigravityエージェントなど）が並行して作業を行う場合、ユーザーの指示負担を最小化するため、以下の連携プロトコルを自律的に実行すること。

### 1. Gitを通じた暗黙の連携
- **作業前の履歴確認**: 新たなタスクに着手する際や、他エージェントの修正を引き継ぐ際は、必要に応じて `git status` や `git log -n 3` で直近のコミットや変更差分を自律的に確認すること。
- **作業後のコミット**: 一連のコード修正や機能実装が完了した場合、後続のエージェントが変更箇所を即座に把握できるよう、自律的に `git add` および明確なコミットメッセージ（例: `[Agent] 部門別ダッシュボードのAPI連携を修正`）でコミットを作成し、状態を保存すること。

### 2. ハンドオフ（引き継ぎ）ドキュメントの活用
- **`AGENT_HANDOFF.md` の更新**: 作業が完了し、他のエージェント（または次のセッション）へ引き継ぎが発生する状況では、プロジェクトルートの `AGENT_HANDOFF.md` を自律的に作成・更新すること。
  - **必須項目**: (1)今回完了した内容と意図、(2)変更した主要ファイル、(3)次に行うべきテストや残課題
- **セッション開始時の自動読み込み**: ユーザーから「続きをやって」「別AIが修正した」と指示された場合、エージェントは推測で動かず、必ず一番最初に `AGENT_HANDOFF.md` を読み込み、コンテキストを100%同期してから作業を開始すること。
